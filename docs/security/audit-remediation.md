## Medium

| # | Finding | Fix | Status |
|---|---------|-----|--------|
| 8 | OAuth callback CSRF: Meta + Monday callbacks accepted a validly-**signed** `state` even when it didn't match the browser's `state` cookie (`stateMatchesCookie \|\| parsedState.valid` / `!parsedState.valid` skip) — since the signing secret is server-wide, an attacker could mint their own valid `state` via `/oauth/start`, get a `code` for their own Meta/Monday account, and trick a logged-in victim into visiting the callback URL, linking the *attacker's* integration account into the *victim's* organization. | Both callbacks now require an exact `state`-cookie match **and** a valid signature (`AND`, not `OR`) — see [`meta/oauth/callback/route.ts`](../../src/app/api/meta/oauth/callback/route.ts) and [`monday/oauth/callback/route.ts`](../../src/app/api/monday/oauth/callback/route.ts). Google and Canva callbacks already required a strict cookie match. | ✅ Fixed |
| 9 | OAuth start routes (`meta`, `monday`, `google`, `canva`) have no `manage_integrations` permission check — any authenticated member (any role) could connect/replace an org's social, calendar, or PM integration. | Added `hasPermission("manage_integrations")` checks to all four `oauth/start` routes; unauthorized callers are redirected back to the relevant settings page with `error=forbidden`. | ✅ Fixed |
| 10 | Active-org data leaks for **multi-org members**: `getInspirationAssets` (creative assets), `getCommunicationsCalendarData` (legacy calendar), and `getVendorById`/`getVendorNameForMetadata` (vendor metadata) queried by membership only, with no filter pinning results to the user's *current* org — a user belonging to two orgs could see org A's inspiration assets / vendor names while viewing org B. Not a stranger cross-tenant leak (RLS still blocked non-members); all three used the session client. | `getInspirationAssets` and `getCommunicationsCalendarData` ([`creative-assets/queries.ts`](../../src/lib/creative-assets/queries.ts), [`communications-calendar/queries.ts`](../../src/lib/communications-calendar/queries.ts)) now scope to the active org's event ids via `getActiveEvents()` / `resolveScopedOrgEventIds()`. `getVendorById` ([`vendors/queries.ts`](../../src/lib/vendors/queries.ts)) now filters `.eq("organization_id", organization.id)` so vendor metadata (e.g. page `<title>`) can't leak another member org's vendor name. | ✅ Fixed |
| 11 | Unsanitized HTML in developer agreements: Owner-authored agreement body HTML (pasted, or `.html`/`.docx` upload) was stored and rendered as-is via `dangerouslySetInnerHTML` to every developer asked to sign, and re-served inline as `text/html` from the app's own origin by the download route — a compromised/careless Owner account (or any other future write path) could stored-XSS every signer. | Added [`sanitizeAgreementHtml`](../../src/lib/developer-agreements/sanitize-html.ts) (`isomorphic-dompurify`, strips `script`/`iframe`/`form`/event handlers/`javascript:` URIs). Applied at write time in [`publishDeveloperAgreementVersionAction`](../../src/lib/developer-agreements/actions.ts) and again at read time in [`queries.ts`](../../src/lib/developer-agreements/queries.ts) + [`render-executed.ts`](../../src/lib/developer-agreements/render-executed.ts) so already-stored rows are covered too. [`/api/developer-agreements/download`](../../src/app/api/developer-agreements/download/route.ts) now defaults `Content-Disposition` to `attachment` (was `inline`) and adds `X-Content-Type-Options: nosniff`; explicit `?disposition=inline` still available for in-app preview links. | ✅ Fixed |
| 12 | Client-controlled Content-Type on public-bucket uploads: brand/school logos, artwork inspiration uploads, event assets, and campaign files all stored `contentType: file.type` (or a data-URL's declared MIME) as-is — a renamed/spoofed upload (e.g. `evil.html` sent with `contentType: "text/html"`, or `.svg`) could be served back from our own origin with an attacker-chosen, script-capable Content-Type. | Added [`resolveSafeUploadContentType`](../../src/lib/uploads/safe-content-type.ts): server derives the stored Content-Type from a filename-extension allow-list only, never from client input, and rejects uploads whose extension isn't recognized. Wired into logo uploads ([`organizations/mutations.ts`](../../src/lib/organizations/mutations.ts)), event assets ([`event-workspace/storage.ts`](../../src/lib/event-workspace/storage.ts) + `mutations.ts`), campaign files ([`campaign-files/storage.ts`](../../src/lib/campaign-files/storage.ts) + `mutations.ts`), and artwork inspiration uploads ([`artwork-v2/actions.ts`](../../src/lib/artwork-v2/actions.ts), [`campaign-builder-v2/inspiration-storage.ts`](../../src/lib/campaign-builder-v2/inspiration-storage.ts)). SVG is excluded everywhere (script-capable). `organization-stickers` already had bucket-level MIME/size enforcement and wasn't changed. | ✅ Fixed |
| 13 | CSRF-able `POST /api/insights/sync`: cookie-authenticated, no CSRF token/Origin check, and a malformed/empty body was treated as a valid "full sync" request — a cross-site `<form>` could trigger a Meta insights sync using a logged-in victim's session. | Added [`isSameOriginRequest`](../../src/lib/security/verify-same-origin.ts) (browsers always send `Origin` on cross-site requests; it can't be spoofed by page script or a form) and reject with 403 on mismatch before any org/auth lookup. | ✅ Fixed |
| 14 | No security headers (`next.config.ts` missing CSP/HSTS/etc.) | Added a `headers()` block in [`next.config.ts`](../../next.config.ts) applied to every route: `Content-Security-Policy` (self + Supabase + Sentry + Vercel Analytics allowlisted; `frame-ancestors 'none'`, `object-src 'none'`, `form-action 'self'`), `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, a locked-down `Permissions-Policy`, and `Strict-Transport-Security` (2yr, preload). Exception: [`/create-with-ai-flyer.html`](../../public/create-with-ai-flyer.html) overrides to `X-Frame-Options: SAMEORIGIN` + `frame-ancestors 'self'` so Create with AI → Flyer can embed the static composer same-origin without blanking the iframe. The CSP keeps `'unsafe-inline'`/`'unsafe-eval'` on `script-src` (Next.js inline bootstrap + no nonce plumbing yet) — closes off framing/foreign-script-origin/MIME-sniffing vectors without a full nonce migration; verified via a local production build + `curl -D-` that headers render and the login/pricing pages load with no off-allowlist script/img/connect sources. Stricter nonce-based CSP is a good follow-up, not a blocker. | ✅ Fixed |
| 15 | Deactivating a member doesn't revoke their session/refresh token | Added [`public.revoke_user_sessions(uuid)`](../../supabase/migrations/20260725100000_revoke_user_sessions.sql) (service-role RPC; deletes the user's `auth.sessions` rows, cascading to `auth.refresh_tokens`) and an app-level [`revokeUserSessionsIfNoActiveMembership`](../../src/lib/auth/revoke-sessions.ts) wrapper that skips the revoke if the user still has an active membership in another org (multi-org users aren't logged out everywhere). Wired into both `updateTeamMemberAction` (status → `deactivated`) and `removeTeamMemberAction` in [`auth/actions.ts`](../../src/lib/auth/actions.ts). Best-effort/non-blocking: a revoke failure never blocks the deactivation itself. Residual risk: an already-issued access token (JWT) is stateless and remains valid for its own short remaining lifetime — this closes the "refresh forever" hole, not the in-flight-token window. | ✅ Fixed |
| 16 | Unsanitized filename in calendar-import upload storage path: `${organizationId}/${Date.now()}-${file.name}` interpolated the raw client-supplied filename directly into the Storage object key. | Added [`sanitizeFilenameForStorage`](../../src/lib/uploads/sanitize-filename.ts) (strips any embedded path segments, non-safe characters, and caps length; matches the pattern already used by event-asset/campaign-file uploads). Applied to both calendar-import upload paths ([`calendar-import/mutations.ts`](../../src/lib/calendar-import/mutations.ts): file upload + ICS-from-subscribe-feed) and the school-setup wizard's inline calendar upload ([`organizations/mutations.ts`](../../src/lib/organizations/mutations.ts)), plus the developer-agreement template upload path which had the same pattern ([`developer-agreements/actions.ts`](../../src/lib/developer-agreements/actions.ts)). Not a cross-tenant traversal risk (bucket RLS already scopes to `{organizationId}/...`) — this is about keeping the stored key well-formed and safe to redisplay/re-download. Covered by [`sanitize-filename.test.ts`](../../src/lib/uploads/__tests__/sanitize-filename.test.ts). | ✅ Fixed |

### Known follow-up (not in this pass)

- **Public bucket → signed URLs migration:** event-assets (and related) still serve public URLs after upload. Migrating to signed/private URLs is a larger storage + client change; app-layer event/org gates above are the primary control for this pass. Track under storage hardening when scheduled.

## Already solid — no action needed

- RLS enabled on all `public` tables; membership-scoped policies (064–067) use `security definer` + `search_path=''` correctly.
- No raw/dynamic SQL across migrations; the one `.rpc()` call is fully parameterized.
- Stripe and Meta webhook signature verification are correct, raw-body based, fail closed.
- No secrets reach the client bundle; `server-only` guards used correctly throughout.
- No permissive CORS; middleware fails closed on protected paths.
- Ask Ralli AI context packs are correctly org-scoped.
