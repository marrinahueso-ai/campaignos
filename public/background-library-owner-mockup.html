Recommended structure (simplest maintainable)

Gate with existing canAccessOwnerOps() (allowlisted email + Owner role) — same as /ops/ai-apis. Not org-scoped. Storage under a private bucket prefix like ops/backgrounds/{assetId}/….

background_libraries Back to School, Fall, Winter, Sports, Generic, Graduation — name, slug, sort_order, active
background_sources Uploaded inspiration/source graphics used to generate variants — storage_path, title, notes
background_assets Each candidate/published bg — status, title, tags[], colors[], season, school_level, usage_count, source_id
background_asset_libraries M2M join only — one asset → many libraries. Avoid duplicating files per collection.
  • Workflow: Upload source → generate variants (async job later) → Review Queue → Approve + assign libraries → Published. Reject / Archive / Restore / hard-delete.
  • Usage: increment usage_count when a school campaign attaches the asset; optional later event log if analytics deepen.
  • Skip for v1: per-org libraries, versioning trees, complex AI job UI — keep generation as owner-triggered action + status on source row.
